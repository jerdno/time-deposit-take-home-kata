# Idempotency key for the Balance Update, stored in the Balance Update's write transaction

A client that retries `POST /v1/time-deposits/balance-updates` after a timeout cannot tell whether the first call applied a month of interest, so a blind retry may apply a second one. The POST takes an optional `Idempotency-Key` header: the first call with a key loads and computes the Balance Update as usual, then, in its one write transaction, claims the key in an `idempotency_keys` table and saves the Balances. A later call with that key returns `204` without running it. Because the key commits or rolls back together with the Balances, a stored key always means a month of interest was applied, and a call that failed can be retried with the same key.

## Considered Options

- **A key parameter on the Balance Update use case.** Simple, but it ties a web retry concern to the Balance Update, and no other endpoint could reuse it. Rejected by the ticket's "cross-cutting, opt-in" requirement.
- **A servlet filter that wraps the request in a transaction.** It would be opt-in by URL with no controller change. But the transaction then spans view rendering and error handling, rollback has to be decided from the response status, and a response flushed before the commit could report success for work that then fails to commit. It would also run in the same filter chain as the access log. Rejected.
- **Claim the key in its own transaction first, with a status (in progress, done).** It allows answering a concurrent duplicate with `409` while the first is running, as the IETF Idempotency-Key draft suggests. But a crash between the two transactions leaves a key stuck "in progress", which needs expiry and recovery. Rejected for now; a stored response with a status belongs to the generic mechanism (ticket 12).
- **One transaction around the whole guarded call, key claimed first.** The simplest way to commit the key with the Balances, but the transaction, and its connection, would then stay open while interest is computed, which ADR 0001 avoids. Rejected.
- **Split the use case into a prepare phase and an apply phase**, and let the run-once mechanism open the write transaction between them. It keeps the computation outside the transaction, but every guarded use case must expose two phases on its in-port only for this. Rejected.
- **A plain `INSERT` and catching the unique violation.** In PostgreSQL the violation aborts the whole transaction, so the replay could not even commit cleanly without a savepoint. Rejected in favour of `ON CONFLICT DO NOTHING`.
- **A shared write helper that claims the key in the use case's write transaction** (chosen). The use case keeps its plain in-port and its own shape (load, compute, then one short write transaction, ADR 0001); it only opens that transaction through `WriteTransaction`. One commit decides both the key and the Balances, and the database's unique index settles concurrent duplicates.
  - `IdempotentRequests` (web adapter) is the part an endpoint opts into: the controller passes it the header and the use case call. Without a key the call simply runs. With one it strips the optional double quotes and calls the `RunOnceUseCase` in-port.
  - `RunOnceService` (application) first reads whether the key is stored, outside any transaction; if it is, the call is a replay and the work does not run. Otherwise it binds the key for the duration of the work, in a `java.lang.ScopedValue` (`IdempotencyKeyScope`, package-private in the application layer), and runs the work with no transaction of its own. It logs a skipped call at `INFO`, so every adapter that uses it gets the same line. Nothing in it knows about the Balance Update.
  - `WriteTransaction` (application) runs a use case's writes in one `TransactionTemplate` transaction. If a key is bound, it first claims it there through the `ClaimIdempotencyKeyPort` out-port. If a concurrent call with the same key committed first, it throws an internal exception: the transaction rolls back, nothing is written, and `RunOnceService` reports a skip. Without a key it is a plain short transaction, so the Balance Update behaves the same whether or not it is guarded.
  - A guarded call writes through exactly one `WriteTransaction`. A second one under the same key is an `IllegalStateException`, raised before it opens (the first has already committed with the key). Guarded work that finishes without any `WriteTransaction` is an `IllegalStateException` too, since its key would never be stored and every retry would run it again. Both are programming errors, answered with a `500`.
  - The persistence adapter claims with `INSERT ... ON CONFLICT (key) DO NOTHING`, under `Propagation.MANDATORY`. A concurrent call with the same key waits on the first call's uncommitted row. It then inserts nothing (the first committed: a replay, `204`, and its computed Balances are dropped) or inserts the key and saves its own Balances (the first rolled back).
  - The key is claimed before the Balance Update's save finds or writes anything, so a same-key duplicate never races the save and never sees the `409` of ADR 0001.
  - Another endpoint opts in the same way: its controller wraps the use case call in `IdempotentRequests.run`, and the use case writes through `WriteTransaction`.

## Consequences

- Two concurrent calls with the same key may both load the Time Deposits and compute the interest; only one writes. The work of the other is thrown away, which is cheap here and rare.
- A concurrent call with the same key holds a request thread and a database connection while it waits, but only for the first call's write transaction, not for its load and calculation.
- The key travels from `RunOnceService` to `WriteTransaction` without appearing in the use case's signature. The binding lives only for the guarded call on its thread; work handed to another thread would not see it.
- The replay returns the same `204` as the original. Nothing is replayed except the status: the endpoint has no response body.
- There is no request fingerprint: the POST has no body or parameters, so every call with a key is the same request. Keys are global, not scoped to an endpoint or a client, because only one endpoint accepts them.
- Keys never expire, so `idempotency_keys` grows by one row per keyed call (about twelve a year at one Balance Update a month).
- A keyed call that loses the optimistic-locking race of ADR 0001 returns `409` and stores no key, so its retry with the same key runs.
- Ticket 12 can lift `IdempotentRequests`, `RunOnceUseCase`, `WriteTransaction` and the `idempotency_keys` table into a generic mechanism (stored responses, fingerprints, expiry) without touching the Balance Update.
